# 知识库文档解析与分段方案

本文用于为知识库构建制定文档解析、分段、元数据和质量检查方案。核心原则是：**先识别文档结构，再按内容语义分段；保留原文出处；用检索任务验证分段是否有效。** 固定长度切块只适合作为超长内容的兜底，不应是唯一策略。

后续切分按本文执行。真实问题检索留到对话功能接上后再做。

## 一、通用处理流程

1. **盘点输入**：格式、语言、文件数量、是否扫描件、页面/表格/图片比例、是否加密或损坏、预期查询类型及更新频率。
2. **抽取结构**：提取标题层级、段落、列表、表格、图注、脚注、页码、时间戳、代码符号、字段名等。保留阅读顺序和元素之间的关联。
3. **清理但不改写事实**：去掉重复页眉页脚、导航和明显噪声；谨慎处理脚注、免责声明、版本号和适用范围，这些可能影响答案。原始文件始终保留。
4. **先按语义单元切分**：按章节、段落组、完整表格、幻灯片、邮件/对话轮次、代码符号或数据记录切。单元过大时，再沿更小的语义边界递归拆分。
5. **补足局部上下文**：块内添加简洁的标题路径、表名/字段名或必要定义。必要时用少量重叠修复边界断裂，不为凑比例机械重复大段文本。
6. **附加出处元数据**：每块都能定位回原文件和原位置，并与文档版本关联。
7. **质检与调优**：抽查块首尾、复杂版面和低置信度区域；用真实问题检查定义、例外、步骤、表格数值及版本能否检索到。

### 推荐的通用元数据

- `source_id`：稳定的文档标识
- `filename`、`format`、`document_title`
- `source_version`、`published_at`、`effective_date`（若可得）
- `page_start/page_end`、`slide_number`、`sheet_name`、`row_start/row_end`、`char_start/char_end` 等位置字段
- `heading_path`：章节层级路径
- `chunk_id`、`chunk_index`、`parent_id`、`previous_id/next_id`（需要顺序或父子关系时）
- `element_type`：正文、表格、图注、代码、邮件、记录等
- `language`、`extraction_method`、`ocr_confidence`（适用时）
- `access_scope`、`owner`、`tags`（依权限和业务需要）

元数据字段应便于过滤和回溯。不要把权限、版本等关键属性只写在正文文本里。

### 分段大小的起点

普通说明性文本可以从每块约 **300–800 tokens** 起步，必要时使用约 **50–100 tokens** 的轻度重叠。它们只是调参起点：FAQ、短记录、代码函数、表格行组往往应更小；一段完整流程或论证可能更大。优先保持语义完整，再满足模型上下文和索引限制。标题路径也计入块长度。

## 二、按文档类型的解析与分段方案

### 1. PDF（数字原生）

**常见内容**：报告、论文、手册、合同、政策、说明书、目录、脚注、表格、双栏排版、公式、图表。

**解析**：优先使用能识别版面和阅读顺序的解析方式；提取页码、字体/标题层级、段落、列表、表格、图注、脚注及链接。双栏文档按栏顺序还原，不能简单按文字坐标从左到右串起来。目录可用于恢复标题层级，但应校验标题与正文对应关系。

**分段**：按标题层级分章节，再以段落或完整论证组分块。表格独立成块并保留表题、列头、单位、注释和页码。公式与变量解释、编号及相邻推导保持关联。图表块保留图题、图注和正文引用；若图像本身承载关键数据，应保留图像链接或生成经校验的描述。

**重点检查**：跨页表格、脚注编号、单双栏混排、页眉页脚误入正文、表格列错位、页码定位准确性。

### 2. PDF/图片（扫描件、传真、拍照）

**解析**：先检测页面方向、倾斜、分栏和页面边界，再进行 OCR/版面识别。保留页码、区域坐标、OCR 置信度；低置信度数字、人名、条款号和表格单元格应标识为待复核。

**分段**：先按页内版面区域识别标题、正文、列表、表格、印章/批注等，再按与数字原生 PDF 相同的语义边界分段。尽量保存文本块到页码/坐标的映射。对无法可靠识别的图表，保留原图引用并说明无法提取，不要编造内容。

**适用**：纸质档案、历史合同、扫描书籍、现场表单、票据。

### 3. Word / DOCX / ODT / RTF

**解析**：读取标题样式、段落、列表编号、表格、页眉页脚、脚注/尾注、批注和超链接。不要只依赖视觉字号推测层级；无样式文档可结合编号和排版推断并标记推断结果。修订模式下需明确采用最终稿、原稿还是保留修订信息。

**分段**：标题及其下属段落形成内容单元；较长章节再按段落组拆分。列表尽量连同引导句和完整条目保留。表格按完整行组切块，重复列头、表名和单位。脚注若改变正文理解，应与对应段落链接或一并纳入块。

### 4. TXT / Markdown / AsciiDoc / 富文本导出

**解析**：保留编码、换行、标题标记、列表、引用、代码围栏、链接和锚点。先识别格式特征，处理网页导出或 OCR 产生的断行与重复空白；不要把代码块或表格当普通散文清洗。

**分段**：优先按标题路径与段落。Markdown 表格以表为单位，超长时按行组并重复表头。代码围栏整体保留。无标题长文本可按段落、主题转折和语义边界聚合，并记录字符偏移。

### 5. Excel / XLSX / XLS / ODS / CSV / TSV

**解析**：检查工作表名、隐藏行列、合并单元格、表头、单位、公式、注释、筛选、日期格式和空值含义。区分公式与缓存结果；根据知识库用途决定保存公式、计算值还是两者。对于 CSV/TSV，推断并校验分隔符、编码、引号和表头。

**分段**：每个表或工作表建立上下文块，说明工作表名、表头、单位和筛选条件；详细数据按完整记录或适度行组切块。每个块重复必要表头，保留行号/主键。避免按固定字符数从行中间截断。宽表可按相关列拆成多个视图，但每块要保留主键及列名，并注明拆分关系。汇总单元格和脚注应与对应数据范围关联。

**适用**：产品目录、指标表、价目表、联系人表、实验数据、财务/运营报表。

### 6. PowerPoint / PPTX / ODP / Keynote 导出

**解析**：保留演示文稿标题、章节/分节、页码、文本框阅读顺序、备注、图表、表格、演讲者注释和对象中的替代文本。文本框的物理位置未必表示逻辑顺序；结合版面和内容判断。若有备注，应区分面向观众的正文与演讲者补充。

**分段**：通常每张幻灯片为一个基本单元，附演示文稿标题、章节标题和页码。连续幻灯片共同描述一个流程或论证时，可合并为小组；单页内容过多时按版面主题拆分，保留页内定位。图表数据与图题、轴标签、单位一起保留。

### 7. HTML / 网页 / Wiki / 邮件归档页面

**解析**：去掉导航、广告、脚本和重复页脚，保留正文、标题层级、列表、表格、代码、链接文字、发布时间、作者和 canonical URL。Wiki 还要保留页面层级、页面版本及相互链接。判断动态页面是否需要抓取渲染后的内容。

**分段**：按主内容区域中的标题和段落分段；将列表、表格、FAQ 问答组作为完整单元。每块保留页面标题、标题路径、URL、抓取时间/页面版本。链接目标的内容如未摄入，不应把链接文字当成目标内容。

### 8. Email / 邮件线程

**解析**：提取发件人、收件人、时间、主题、正文、引用链、附件及附件关系。标准化邮件头但保留原始时间和时区。剔除重复引用正文时保留必要的上下文线索；签名、免责声明可按业务需求处理。

**分段**：短邮件按单封邮件；长邮件按标题/段落。线程按消息顺序存储，每条消息保留邮件 ID、父/线程 ID、发件人、时间和主题。引用内容和回复应保持可追踪关系，避免把不同发件人的观点合并成无来源文本。附件作为独立文档摄入，并附所属邮件元数据。

### 9. Chat / IM / 会议纪要与问答记录

**解析**：保留参与者、时间戳、频道/会话 ID、回复关系、编辑/删除状态、引用、文件附件和反应等必要上下文。导出文本若缺失参与者或时间信息，应记录缺失。

**分段**：优先以完整问答或主题连续的消息组为块；长线程根据话题转折切分。每块保留参与者和时间范围，线程/回复关系用 ID 表示。不要跨主题把消息拼成脱离来源的段落。会议纪要可按议题、决定、行动项分块，并保留负责人和期限。

### 10. 源代码与配置文件

**解析**：按语言解析语法结构，提取仓库、路径、模块、类、函数、方法、注释、签名、依赖和版本。避免只靠通用文本切分破坏语法单元。配置文件需保留键路径、环境/版本上下文；注意密钥与敏感值按访问控制策略处理。

**分段**：函数、方法、类或配置对象是常用单元。超长类按成员拆分，并在每块附模块/类路径及必要的接口或类型信息。代码与描述该代码的注释、文档字符串保持关联。仓库级说明可单独成块并引用相关路径。

### 11. JSON / XML / YAML 及 API/日志导出

**解析**：保留层级路径、字段名、类型、数组元素关系、命名空间、时间戳和 schema/version。JSON/XML 不应只展平成键值文本；需标明父对象和数组索引或实体 ID。日志解析保留事件时间、级别、服务、trace/request ID 和结构化字段。

**分段**：按完整对象、数组中的实体或逻辑事件组切分；超大数组按元素组切，重复 schema/字段说明。记录块附 JSONPath、XPath、键路径或行号。日志按 trace、事务或短时间窗口聚合，避免把无关事件混在一起。

### 12. 音频/视频、字幕、访谈与转录稿

**解析**：语音识别结果保留说话人、时间戳、语言和置信度；视频保留时间码、场景/章节、字幕及关键画面说明。区分人工校订稿与自动转录。非语音内容若重要，也应通过适当的描述或标签记录。

**分段**：按话题边界或自然停顿切分，通常以一段完整发言/问答为单位；附起止时间码、说话人和媒体 ID。不要只按固定秒数切导致句子断裂。视频中画面与同期对话互补时，保持时间关联。

### 13. 表单、票据、合同和其他结构化业务文档

这类文档常同时包含字段、表格、自由文本和签字/印章。先识别文档类型与版式，再抽取字段和值，并保留字段标签、页面坐标、置信度及文档 ID。

分段可按表单区域、合同条款、票据字段组或业务记录；金额、币种、日期、单位、主体名称必须与标签同时保留。合同的定义、义务、例外、期限和适用范围应保持相互可检索，并保留条款号与页码。

## 三、跨格式的特殊内容

- **表格**：始终保留表名/标题、表头、单位、脚注和适用筛选。跨页表格要识别重复表头并连接；切块时每块重复必要列头。
- **图表与图片**：保存原始图片引用、图题/图注、邻近解释及其页码或位置。若使用图像描述，应标明其为生成/识别的辅助描述，不能冒充原文。
- **公式与数学符号**：保留公式编号、变量定义、单位和相邻推导；检查 OCR 对上下标、负号、希腊字母的误识别。
- **脚注、批注、附录**：当其包含例外、限定或补充证据时，连接回主文位置，避免被清理掉。
- **版本与时效**：同一文档多个版本要分别保留版本元数据；检索时可按有效日期筛选。不要无标记地把不同版本合并。
- **多语种**：保留原文语言和脚本；若另生成翻译文本，记录翻译语言及来源关系，不要覆盖原文。
- **权限**：继承源文件访问范围到每个 chunk，避免切分或派生文件导致权限扩大。

## 四、质量检查清单

### 抽取检查

- 是否覆盖所有页面、工作表、幻灯片、邮件和附件？
- 阅读顺序、标题层级、列表编号是否正确？
- 表格行列、表头、单位、脚注是否对应？
- OCR 中的数字、日期、姓名、条款号和负号是否可靠？
- 图表、公式、批注和脚注是否遗漏？

### 分段检查

- 每块脱离原页仍能知道主题和适用范围吗？
- 定义与术语、问题与答案、条件与例外、步骤与前置条件是否仍在一起？
- 边界处有没有半句话、孤立标题、缺失表头或被拆开的代码结构？
- 是否有过多重叠、重复页眉页脚或重复引用邮件？
- 是否可以通过元数据回到准确页、段、行、幻灯片、代码路径或时间码？

### 检索验证

针对语料准备一组代表性问题，包括精确事实、概念解释、条件/例外、跨段落关系、表格查值和版本查询。检查命中块是否包含完整证据及正确出处。若检索只命中孤立关键词，优先检查结构和上下文，而非单纯增大块长度。

对话检索接上之后再做这一项。

## 五、建议的块数据结构示例

```json
{
  "chunk_id": "doc-123:p12:sec-2.1:03",
  "source_id": "doc-123",
  "filename": "操作手册.pdf",
  "format": "pdf",
  "document_title": "操作手册",
  "heading_path": ["设备维护", "故障处理", "过热告警"],
  "element_type": "paragraph_group",
  "text": "设备温度超过阈值时……",
  "page_start": 12,
  "page_end": 12,
  "chunk_index": 17,
  "language": "zh",
  "extraction_method": "layout_parser",
  "source_version": "2026-03"
}
```

不同格式可用相应位置字段替换页码，例如 `sheet_name + row_start/row_end`、`slide_number`、`json_path`、`code_path` 或 `time_start/time_end`。

## 六、落地建议

1. 先选取每种主流格式的代表性样本，覆盖普通文本、复杂版面和异常情况。
2. 保存解析后的结构化中间结果，便于重新分块而无需重复 OCR/解析。
3. 让 chunk 能回溯到原始文档，并将权限、版本与来源一起传入索引。
4. 以具体检索问题评估准确性和上下文完整度，再调整切分边界和大小。
5. 对解析器升级、OCR 参数变更和 chunk 规则变更保留版本，便于重建索引和比较效果。
